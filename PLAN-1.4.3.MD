## 2. Инструменты замера

- **`crates/core/examples/ocr_accuracy.rs`** (уже написан, ещё не прогнан до конца). Кадр идёт тем же путём, что
  и в приложении: детектор → RapidOCR по полям (`read_field` со «вторыми шансами») → `observe_ocr_result` /
  `complete` → пересканы → размещение (`place_regions`, приближённые метрики вместо Qt). Выдаёт:
  - **CER** — для каждой записи разметки ошибка ближайшего куска чтения (регистр и пробелы не важны);
  - **пропущено** — записи с CER > 0,3;
  - **лишние поля** — прочитанное, чего нет в разметке (кусок сцены, мусор);
  - **покрытие** — какую долю исходного поля закрывает плашка перевода;
  - время на кадр; картинку с рамками полей (зелёные — прочитаны, красные — отброшены).
- **Доработки инструмента:**
  - JPEG: конвертация в PNG в `tmp/acc/frames` (декодер JPEG в проект не добавляем — так уже решено раньше);
  - разбивка метрик по классам и по наборам (рабочий/контрольный);
  - сравнение области наложения с эталоном: полнота (`recall`) и лишняя площадь (`excess`) по пикселям эталона;
    плашки берутся из размещения, рендер Qt не нужен;
  - вывод в JSON (`tmp/acc/<прогон>/report.json`), чтобы сравнивать прогоны до/после построчно;
  - прогон в фоне, по одному кадру на процесс или с `--frames=`: весь набор — минуты, и это не должно блокировать
    работу.

## 4. Улучшения распознавания (гипотезы, каждая проверяется замером)

- **R1. Текст на сложном фоне.** Глобальный порог Оцу на фото и полупрозрачных окнах делит не «текст/фон», а
  «светлое/тёмное». Проверить, какие пропуски закрывает локальный проход (`local_ink.rs`), и при необходимости
  считать маску по окну диалога (локальная полярность внутри найденного блока).
- **R2. Кадрирование поля для OCR.** Запас вокруг строки, увеличение мелкого текста (кегль ниже ~16 px) перед
  RapidOCR, снятие обводки/тени для чтения. Проверка: CER на мелком тексте и время.
- **R3. Группировка строк.** Многострочный диалог должен быть одним полем, имя — отдельным, варианты ответа —
  отдельными строками. Ошибки группировки видны по разметке: одна запись разметки разбита на два поля или две
  записи читаются из одного поля.
- **R4. Фильтры чтения.** Настоящий текст, отброшенный порогом уверенности или «осмысленностью» (короткие имена,
  числа в интерфейсе), — пересмотреть пороги по рабочему набору, не ослабляя защиту от мусора (лишние поля не
  должны расти).
- **R5. Лишние поля.** Сцена, принятая за текст: признаки, которые отличают её на рабочих кадрах (нет строк с
  постоянной высотой, нет межбуквенных промежутков), — как правило детектора с юнит-тестом.

## 5. Улучшения наложения

- **O2. Кегль и межстрочный интервал** ближе к эталону (у эталонов перевод того же размера, что оригинал); длинный

## Решение архитектора

Дата: 2026-11-14. Предмет: правило фрагментов в `duplicate_owner` (`crates/core/src/layout/place.rs:581`,
`FRAGMENT_RATIO` — `:583`, тест — `:990`).

**Решение: оставить без изменений. Пороги (`FRAGMENT_RATIO` = 4, вложенность 0,9, длина ≥ 2) не трогать.**

**Что проверено** (по `tmp/acc/base/report.json` и `tmp/acc/r1/report.json`; правило смоделировано по полям
`rect`/`text` базового отчёта на всех 16 кадрах):

- На кадрах 0–9 новое правило срабатывает два раза, на разных кадрах и разными ветками:
  - кадр 8, `0 0` внутри реплики — ветка похожих символов (`00` ↔ `oo`);
  - кадр 6, `ED` внутри `NORA ANOINTED Hunter common` — ветка точного совпадения двух символов.
  - `de p` на кадре 8 (после нормализации 3 символа) снимало ещё старое правило.
- Ни одно из этих полей не было видно и до правки (`plate: null` в базовом отчёте). Правило убирает не поле, а
  конкурента: плашка владельца упиралась в «чужой» исходный текст. Кадр 8: реплика стояла рядом с оригиналом
  (`cover` 0,0 → 1,0). Кадр 6: поле не рисовалось вовсе (`plate` null → есть).
- Остальные восемь рабочих кадров совпадают с базой по числу полей, пропускам, лишним полям, recall и excess.
- `r1` и `r2` побайтно одинаковы; `cargo test --release -p lipa-core --lib layout::place` — 27 из 27.

**Подгонка под кадр 8?** Нет: класс общий — детектор вырезал кусок строки внутри абзаца, кусок прочитан повторно.
Это подтверждает кадр 6 (другая игра, другая ветка). Но у каждой ветки по одному примеру, а `FRAGMENT_RATIO`
данными не проверен: фактические отношения длин 12 и 60, любой порог от 2 до 12 даёт тот же отчёт.

**Оговорки к заявленным метрикам:**

- «Лишние поля и пропуски не изменились» ничего не говорит о правиле. `spurious`, `missed` и `fields` считаются
  по `frame.blocks` до размещения (`ocr_accuracy.rs:243–278`), а правило работает внутри `place_regions`.
  Измениться они не могли.
- Юнит-тест не покрывает ветку, которая дала прирост на кадре 6: `de p` в тесте — три символа, это старое правило.

**Цена:** перебор окон только для пар с вложенностью ≥ 0,9; на 16 кадрах таких пар четыре. Время отдельно не
замерялось.

**Риск регрессии:** настоящая подпись из двух символов (`OK`, `No`, `x2`, счётчик `10`), лежащая на ≥ 90 % внутри
прямоугольника длинного чтения (короткая последняя строка абзаца, склеенный блок интерфейса, как на кадре 7).
В английской фразе от 8 символов почти всегда есть `on`, `no`, `to`, а `10` похоже на `lo`. Единственная защита —
геометрия. На 16 кадрах таких полей из разметки нет: ни ложных срабатываний, ни проверки этой защиты.

**Проверки на контрольном наборе 10–15** (пороги по ним не подбираются):

1. Прогон `tmp/acc/run.sh c1 --frames=10-15`. Ожидание по модели: правило не срабатывает ни разу, записи кадров
   10–15 совпадают с базовыми построчно. Любое отличие — остановка и разбор. Следствие: контрольный набор
   подтверждает только отсутствие вреда, пользу он показать не может.
2. Доработать `ocr_accuracy`: писать в отчёт кадра `dropped` (текст, причина, владелец, ветка — точное
   совпадение или похожие символы). Без этого срабатывания видны только косвенно.
3. Критерий по записям разметки: ни одна запись без `unsure`, у поля которой в базе есть плашка, её не теряет.
4. По полям: `cover` не уменьшается ни у одного поля с плашкой; по кадрам 10–12 recall не ниже, excess не выше
   базы; кадры 13–15 (без эталонов) — только сравнение плашек.
5. Каждое срабатывание на 10–15 смотреть глазами по `tmp/acc/c1/*.png`: фрагмент должен быть пикселями текста
   владельца.
6. Регрессии `engine.exe` и `CrossxMars`: `inplace_ocr_ownership`, `inplace_detection`, `inplace_dialogue_change`.

**Добавить юнит-тесты** (синтетика, без слов из кадров):

- два символа, точное совпадение, внутри длинного чтения — повтор (случай кадра 6);
- два символа внутри короткого владельца (длина меньше 4×) — остаётся полем;
- два символа внутри прямоугольника длинного чтения, которых в его тексте нет, — остаётся полем.

**Если на контроле найдётся ложное срабатывание:** не менять числа, а сузить формулировку и вернуться на рабочий
набор. Первый кандидат — оставить для двух символов только ветку похожих символов. Цена сужения известна заранее:
кадр 6 вернётся к recall 0,572.
