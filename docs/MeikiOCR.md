# MeikiOCR (необязательный движок для японского)

MeikiOCR — модели [rtr46/meikiocr](https://github.com/rtr46/meikiocr) для японского текста
видеоигр и визуальных новелл: детектор строк (D-FINE на MobileNetV4) и распознаватель, который
сразу находит отдельные символы. LipaX выполняет их **в своём процессе** через ту же ONNX Runtime,
что и [RapidOCR](RapidOCR.md): без Python, без отдельного процесса. Читается только японский
(основной язык распознавания должен быть `jpn`).

Выбор: «Настройки → Распознавание → Движок распознавания → **MeikiOCR (японский, игры)**»,
для отдельной области — в её настройках. В режиме **Авто** MeikiOCR работает «вторым мнением»
для японского, **если его модель скачана** (см. ниже).

## Установка

1. Библиотека ONNX Runtime — как для RapidOCR: `sudo pacman -S onnxruntime-cpu`
   (поиск библиотеки и переменные `LIPAX_ORT_LIBRARY` / `ORT_DYLIB_PATH` описаны в [RapidOCR.md](RapidOCR.md)).
2. Модель — кнопка **«Скачать»** в том же блоке настроек (около 46 МБ). Модели не входят в пакет
   и никогда не скачиваются сами. Файлы берутся с Hugging Face (`rtr46/meiki.text.detect.v0` и
   `rtr46/meiki.txt.recognition.v0`) по **закреплённым ревизиям**, размер и SHA-256 каждого файла
   проверяются перед установкой (так же, как у RapidOCR и Bergamot: временный каталог, `.part`,
   атомарная замена).

   | Файл | Назначение | Размер |
   |---|---|---:|
   | `meiki.text.detect.v0.1.960x544.onnx` | детектор строк | 14,5 МБ |
   | `meiki.text.rec.v0.960x32.onnx` | распознаватель горизонтальных строк | 18,6 МБ |
   | `meiki.text.rec.v0.vertical.32x480.onnx` | распознаватель вертикальных колонок | 12,9 МБ |

   Модели лежат в `~/.local/share/LipaX/ocr-models/meiki-ja/`. Удалить их можно кнопкой «Удалить».
3. Лицензия весов — **LGPL-3.0** (код MeikiOCR — Apache-2.0). Веса не входят в пакет LipaX,
   пользователь скачивает их сам; лицензия указана в каталоге и в окне загрузки.

В режиме **Авто** с японским языком блок настроек предлагает необязательную модель MeikiOCR
отдельной строкой. Пока она не скачана, японский читает RapidOCR (`ch-mobile`).
Если задан **основной язык, отличный от японского**, MeikiOCR сообщает об этом и ничего не читает.

## Как идёт распознавание

Это порт эталонного конвейера `meikiocr`:

1. Кадр вписывается в 960×544 без искажения (чёрные поля справа и снизу), порядок каналов BGR,
   значения 0–1. Детектор получает кадр и его размер и возвращает рамки строк (не более 64); порог 0,5.
2. Рамки сортируются сверху вниз. Рамка выше, чем шире, — **вертикальная колонка**.
3. Горизонтальная строка масштабируется до высоты 32 (не шире 960). Распознаватель возвращает
   символы (метка — код Unicode, словаря и CTC нет) с рамками и уверенностью; порог 0,1.
4. Вертикальная колонка масштабируется до ширины 32. Если после этого она выше 480, её режут на
   перекрывающиеся сегменты по 420 (перекрытие 64), иначе читают целиком.
5. Кандидаты одной строки прореживаются подавлением немаксимумов: остаётся самый уверенный, а
   перекрывающийся с ним больше чем на 30 % короткого отбрасывается. Затем символы идут по порядку
   вдоль строки; восемь известных перестановок пар (`談冗` → `冗談` и т. п.) исправляются.
6. Колонки вертикального текста идут справа налево.

Уверенность строки — среднее по символам. Автоматическая бинаризация для MeikiOCR не применяется:
модели обучены на цветных кадрах. Отдельного нижнего порога уверенности, как у RapidOCR (50), нет:
символы с оценкой ниже 0,1 отсеиваются самим конвейером.

## Настройки

Число потоков и GPU общие с RapidOCR («Потоки ONNX Runtime», «Видеокарта»): значение 0 — половина
ядер, но не больше 4, без активного ожидания потоков между кадрами. Модель загружается при первом
распознавании (до 2 моделей в памяти); вертикальный распознаватель — только когда на кадре есть
вертикальный текст.

## Результаты

Ryzen 5 5600, ONNX Runtime 1.29.0, `--release`, 4 потока. Японская строка («こんにちは、旅人さん。
どこへ行くのですか？», Noto Sans CJK, 36 px) вставлена в игровой кадр (тёмный градиент с зерном).

| Кадр | Движок | Задержка, мс (медиана) | CER |
|---|---|---:|---:|
| 1280×200 | MeikiOCR | 63 | 0.048 |
| 1280×200 | RapidOCR (PP-OCRv5 `ch-mobile`) | 53 | 0.048 |
| 1280×200 | Tesseract 5.5.3 | 2637 | 3.000 |
| 1920×1080 | MeikiOCR | 81 | 0.048 |
| 1920×1080 | RapidOCR (PP-OCRv5 `ch-mobile`) | 283 | 0.048 |
| 1920×1080 | Tesseract 5.5.3 | 57360 | 53.952 |

На этой чистой синтетической строке точность MeikiOCR и RapidOCR одинакова; MeikiOCR примерно в 3,5 раза
быстрее на полном кадре, потому что детектор всегда работает на 960×544, а RapidOCR — до 1600 px по длинной
стороне. Преимущество MeikiOCR на реальных шрифтах игр и манги (то, ради чего он обучен) этим тестом не
проверено: настоящих скриншотов игр в репозитории нет. Строки Tesseract и RapidOCR — из замера в
[RapidOCR.md](RapidOCR.md) (тот же кадр и тот же текст).

Единственная ошибка — полноширинный знак «？», который модель читает как «?» (CER 0,048 из-за одного
символа из 21). Остальные строки (три разные фразы, кадры 1280×200 и 1920×1080, размеры текста
20–64 px, три строки в одном кадре) читаются без ошибок, уверенность 91–97 %.

Вертикальный текст — бета-функция моделей (так пишут и авторы). Плотно набранные колонки
(как в играх) читаются с CER 0–0,08; колонки с большими просветами между знаками — хуже
(CER до 0,4), длинная колонка читается сегментами с несколькими ошибками. Это ограничение моделей,
а не конвейера.

## Проверка

Юнит-тесты (геометрия, подавление, декодирование, каталог, сообщения об ошибках) не требуют моделей:
`cargo test -p lipa-core`. Тесты на настоящих моделях (`#[ignore]`):

```bash
cargo run -p lipa-core --example ocr_model -- download meiki-ja     # те же проверки, что у кнопки
LIPAX_RAPID_TEST_MODELS=~/.local/share/LipaX/ocr-models \
cargo test --release -p lipa-core --test meiki_native -- --ignored --nocapture --test-threads=1
```

Текст для тестов рисует Rust (`tests/common`, шрифт Noto Sans CJK из пакета); Python не нужен.

## Каталог

Записи MeikiOCR лежат в том же `crates/core/src/ocr/ocr_models_catalog.json` (поле `engine`:
`meikiocr`). Каталог обновляется программой `cargo run -p lipa-core --example update_catalogs -- ocr`:
она читает только список файлов Hugging Face (размер и SHA-256) и закрепляет ревизии, модели не
скачивает. Новая версия моделей появляется в приложении вместе с новым каталогом.
